## 2. Dataset Source & Acquisition
IO-VNBD (Inertial Odometry Vehicle Navigation Benchmark Dataset) is a public benchmark recorded with a research vehicle on public roads in the United Kingdom, Nigeria and France. Per the README shipped inside the dataset (**VERIFIED_FROM_DATASET_DOCUMENTATION**):

- sensors include a GPS receiver, inertial sensors and wheel-speed sensors on the vehicle, plus the inertial sensors and GPS receiver of an Android smartphone **sampling at 10 Hz**;
- approximately **40 hours over 1,300 km** of vehicle-extracted data and **58 hours over 4,400 km** of smartphone-recorded data;
- scenarios include traffic, roundabouts and hard braking across country roads and motorways.

The local tree `data/IO-VNBD_dataset/IO-VNBD-master/` is a ZIP export of the upstream GitHub repository, which is why it carried only LFS pointer stubs. Actual objects were fetched via the Git LFS batch API of the official upstream repository `https://github.com/onyekpeu/IO-VNBD.git` (**VERIFIED_FROM_OFFICIAL_SOURCE**). Because an LFS `oid` *is* the SHA-256 of the content, every one of the 564 downloaded objects was hash-verified before being written. See `data/metadata/io_vnbd/acquisition_manifest.csv`.

The original pointer tree was left byte-for-byte untouched and remains the provenance record; content was materialized into a separate directory.

## 9. Timestamp & Sampling Analysis
Rates below are **measured**, not assumed. The rate is derived from the *median* inter-sample interval so that occasional large gaps do not understate cadence.

- Smartphone: median 10.0000 Hz (min 2.0000, max 1000.0000, n=240)
- Vehicle: median 10.0000 Hz (min 10.0000, max 10.0000, n=323)

The **median** matches the 10 Hz nominal rate stated in the dataset README, so the documented rate is corroborated rather than taken on trust — **but the median hides real heterogeneity.** The dataset is not uniformly 10 Hz:

| Stream | Measured rate family | Streams |
|---|---|---|
| smartphone | unknown | 1 |
| smartphone | ~10 Hz | 229 |
| smartphone | ~1000 Hz | 2 |
| smartphone | ~2 Hz | 8 |
| smartphone | ~24 Hz | 1 |
| vehicle | ~10 Hz | 323 |

**The vehicle stream is uniformly ~10 Hz. The smartphone stream is not**: alongside the ~10 Hz majority there are distinct families recorded at roughly 2 Hz, ~24 Hz and ~1000 Hz (1 ms sampling). Phase 2 must read the measured rate per file from `sampling_report.csv` rather than assuming 10 Hz, and must decide explicitly how to handle the non-10 Hz files (resample, or exclude with justification).

### Column misalignment — 1 file(s)

In these files **not one value in the timestamp column parses as a number**, despite the file having many rows. Inspection confirms the cause: an extra empty field early in each data row shifts every subsequent value one column to the right relative to the header, so the header label on every channel past that point is wrong (**VERIFIED_FROM_FILE**).

This is silent corruption — the file parses cleanly and only the *values* are mislabelled. **Phase 2 must either repair the shift explicitly or exclude these files**; reading them by column name yields wrong data with no error.

**Duration does not reconcile with the dataset's headline figures.** Measured file time totals 244.7 h (148.0 h de-duplicated), against the README's ~40 h vehicle + ~58 h smartphone ≈ 98 h. **Two different clocks exist and they are not interchangeable (VERIFIED_FROM_FILE):**

## 11. GNSS Availability & Outages
**No file anywhere in IO-VNBD annotates GNSS outages** — there is no outage metadata, marker column, or accompanying documentation of induced dropouts (**VERIFIED_FROM_FILE**: the full file inventory contains only CSVs, JPGs and three documentation files). Consequently:

- every interval in `gnss_outages.csv` has `source = observed_missingness`;
- **none** is labelled `documented`;
- confidence is recorded as `observed_high` — the *absence of a fix* is measured with certainty, but the *cause* (tunnel, urban canyon, logger fault) is **UNVERIFIED**.

- Streams with a GNSS field: **564/564**
- Streams with ≥99.9% availability: **564**
- Streams with 0% availability: **0**
- Total observed gap intervals (≥1.0 s): **0**

A fix is counted as valid when latitude and longitude are both present, finite, and not exactly (0, 0) — the classic 'no fix' sentinel.

### GNSS position staleness — a 100% fix rate is NOT a 10 Hz position source

Availability counts rows that *carry* a position. It does not ask whether that position is **new**. Measuring how often latitude/longitude actually *change* gives a very different picture (**VERIFIED_FROM_FILE**):

| Stream | Median position-update rate | Median update interval | Streams |
|---|---|---|---|
| smartphone | 0.1111 Hz | 9.00 s | 231 |
| vehicle | 9.9463 Hz | 0.10 s | 323 |

**The smartphone GNSS position is forward-filled between updates that arrive roughly two orders of magnitude more slowly than the 10 Hz row rate.** The vehicle reference position, by contrast, genuinely refreshes at ~10 Hz. Consequences for Phase 2:

- consecutive smartphone GPS rows are overwhelmingly duplicates, so treating them as independent 10 Hz fixes would massively overstate the GNSS information available;
- the **vehicle stream is the high-rate position reference**, not the smartphone;
- a smartphone-only navigation solution is effectively dead-reckoning between sparse position updates even when a 'fix' is present on every row.

Held-position spans of at least 30 s were recorded as intervals in `gnss_outages.csv` with `source = observed_position_hold`: **419** such span(s) were found. These are the closest thing in IO-VNBD to a GNSS outage, but they are **staleness, not loss of fix**, and are labelled accordingly.

## 19. Implications for Phase 2
0. **Split on content, never on file path.** 235-odd files are byte-identical duplicates of others (§6a); a path-based train/test split leaks data outright.
1. **Never assume UTF-8.** Read smartphone CSVs with a cp1252 fallback, or column lookups will fail on `m/s²` and `Â°`.
2. **Strip column names.** Every header field after the first carries a leading space; match on normalized names, not raw ones.
3. **Do not `float()` the satellite column.** Parse `"a / b"` or drop it.
4. **Match session ids case-insensitively** (`S-Vta11` ↔ `V-vta11`).
5. **Handle two different clocks.** Smartphone elapsed-ms and `DATE`, vehicle seconds-of-day. The `DATE` millisecond separator is a colon.
5a. **Read the measured rate per file.** The smartphone stream includes ~2 Hz, ~24 Hz and ~1000 Hz families alongside the ~10 Hz majority (§9).
5b. **Segment discontinuous files.** Some streams concatenate several trips; split them on the large timestamp jumps instead of integrating straight through.
5c. **The smartphone GNSS position is ~0.1 Hz, forward-filled** — not a 10 Hz fix source (§11).
6. **Measure the S↔V offset per pair.** Most pairs are near-aligned, but a minority are shifted by ~1 h and many show drift; never hardcode an offset.
7. **Treat GNSS gaps as observed, not labelled.** If Phase 2 needs outage scenarios, it must *synthesize* them from continuous data and say so — the dataset supplies no ground-truth outages.
8. **Do not drop 'outlier' rows reflexively.** High accelerations are plausible vehicle dynamics; see the classifications in `range_findings.csv`.

## 20. Recommended Phase 2 Data Contract
_Recommendations only — nothing below is implemented in Phase 1._

**Smartphone signals safe to rely on** (present in every smartphone file scanned, VERIFIED_FROM_FILE):
`GPS LATITUDE`, `GPS LONGITUDE`, `GPS ALTITUDE`, `GPS SPEED`, `GPS ACCURACY`, `GPS ORIENTATION`, `TIME SINCE START (ms)`, `DATE`, `ACCELEROMETER X/Y/Z`, `GRAVITY X/Y/Z`, `GYROSCOPE Yaw/Pitch/Roll`, `MAGNETIC FIELD X/Y/Z`, `ORIENTATION Yaw/Pitch/Roll`.

**Vehicle/reference signals safe to rely on:**
`Time Since Start of Day`, `Latitude`, `Longitude`, `Velocity`, `Heading`, `Height`, `Vertical velocity`, `Sample period`, `Steering Angle`, `Wheel Speed FL/FR/RL/RR`, `Yaw Rate`, `Indicated Vehicle Speed`, `Indicated Longitudinal/Lateral Acceleration`, plus powertrain/chassis channels (`Gear`, `Engine Speed`, `Brake Pressure`, `Handbrake`, `Clutch Position`, `Accelerator Pedal Position`, `Battery Voltage`, `Coolant/Air Temperature`).

**Verified timestamps:** elapsed-time and seconds-of-day columns. The vehicle stream is uniformly ~10 Hz; the smartphone stream is ~10 Hz for the large majority of files but not all (§9) — read the rate per file.

**Reliable synchronized pairs:** the 216 paired sessions, subject to per-pair offset measurement (see `synchronization_report.csv`); prefer pairs classified `constant_offset` with near-zero drift, and treat `variable_offset_possible_drift` pairs as needing time-varying alignment.

**Known GNSS outage information:** none. There is **no loss of fix anywhere in the dataset and no documented outage ground truth**. `gnss_outages.csv` contains only observed *position-hold* (staleness) intervals. Any outage scenario Phase 2 needs must be synthesized and labelled as synthetic.

**Fields NOT safe to assume:**
- a numeric satellite count on the smartphone stream;
- UTF-8 encoding;
- a timezone-qualified absolute timestamp;
- country, road type, or scenario semantics;
- that an S/V pair is sample-aligned without checking;
- that any gap in GNSS was an intentional/annotated outage.
